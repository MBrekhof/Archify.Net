Which modules does Archify finalize go through, and how is the old artifact kept safe on failure?

Long image

A

Answer

finalize is an orchestrator, not a renderer. runFinalize calls the three subcommands deliver → check → browser-check in order (validate runs inside deliver). Each gate uses sha256 and receiptId to confirm its receipt is bound to this artifact. The first failure stops the run. The old artifact is replaced only at deliver's commit point. The new HTML is first rendered and checked in a .archify-delivery-* staging area in the same directory. At commit the old file is backed up, then the new one is swapped in with a hard link. A failure midway rolls back automatically. If even the rollback fails, the recovery directory is kept.

  1. All three gates reuse the same CLI; finalize checks each receipt's type, byte count and hash.1
  2. Nothing is written to the target path before commit; at commit it backs up first, then linkSync, and aborts on any binding mismatch.2
  3. The delivery lock and the pending journal make an interruption fail closed: concurrent runs are refused, leftover state is not trusted.3
  4. Limit: a check or browser-check failure after a successful commit does not roll back; the old artifact is kept only up to the commit point.

Applies toArchify @ 82c47cabin/finalize.mjs + archify.mjsexplainer has no browser-check gate by default

  • brw → rec
  • chk → brw · pass

  • commit → chk · pass
  • del → commit
  • snap → del

An explainer candidate is first compiled by prepareExplainerInput into a frozen bundle, and before and after each gate its dependencies are rechecked as unchanged. Native diagrams run all three gates by default; an explainer runs only deliver + check, and the browser gate opens only with --browser-check.

  1. commandFinalize parses args ↗

    Parses quality, repo and out-dir; precompiles an explainer into a frozen bundle; starts a bounded update check in parallel.

  2. Snapshot candidate, open receipt ↗

    Records the input sha256; both receipt paths are captured atomically before writing.

  3. Lock, journal, staged render ↗

    Takes the delivery lock and writes the pending journal; rendering and self-checks run in staging; any failing gate stops the run and writes diagnostics.

  4. check strict recheck ↗

    Runs the strict checks once provenance=current and the sha matches, then the browser gate.
